# Payment and Guest navigation correction

The previous verifier first read `used_receipts/{code}` from Firestore before looking up PayHero. The repository rules contained no receipt match, so even a nonexistent receipt read was denied. The catch block described that denial as a connection failure, causing retries to repeat the same failure. Live rule state must be verified during deployment; changing an APK alone cannot repair backend permissions.

To reject copied or fabricated payment codes even from a modified app, verification now runs at the existing website's authenticated `/api/payments/verify` service. The phone sends a Firebase ID token, exact receipt, fixed plan ID and persisted account/plan checkout reference. The server verifies revoked/anonymous tokens, checks the account-bound reference, exact merchant-confirmed receipt, completed incoming KES status and sufficient whole-shilling amount. Receipt consumption and membership mirrors commit atomically through Firebase Admin; a retry cannot extend expiry twice. Clients cannot write any paid approval document under the new rules.

Signed-in Guest had been treated as signed out in the My Netflix banner and TV-link action. Those actions now use authentication state. Guest sees View Plans, while a signed-out viewer still sees Sign In. Download/start/resume and Downloads setup now display an upgrade dialog, then navigate to plans only if selected; authentication follows that explicit selection when required.

Validation: 12 server payment regressions passed, including another merchant's successful receipt, copied/unmatched/pending/underpaid/refunded receipts, conflicting status/ledger evidence, concurrent idempotency, renewal and failed atomic commits. Eighteen Firestore emulator regressions passed, including client paid-membership forgery rejection, private receipt reads, Guest registration and preserved discovery/device rules. Full Android unit/lint results are in `validation.json`.

The production payment service and server-only database rules are deployed. A production negative check rejected a fabricated code and a real receipt submitted from a different account; no membership was created and the temporary QA account was deleted. No payment was made during testing. Successful activation using a customer's existing account-bound receipt still needs confirmation after installing the update; customers should retry their existing receipt rather than pay again.

Every new redemption requires an exact receipt in the authenticated merchant ledger, even when the transaction-status endpoint reports success. Ledger amount, currency, incoming direction and any checkout references are checked; conflicting or missing evidence grants no membership. The public Lipwa checkout bundle confirms that the app's `reference` query parameter is passed to PayHero's `external_reference`.
